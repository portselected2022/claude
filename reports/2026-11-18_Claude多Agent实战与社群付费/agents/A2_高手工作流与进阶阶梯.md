# A2 高手工作流与进阶阶梯

> 编制：A2 ｜ 日期：2026-11-18 ｜ 第一轮（R1）取证备忘录
> 实际检索：WebSearch 14 次（13 次返回结果，第 14 次因平台限额报错，按已用计）；WebFetch 10 次（8 次读到原文，1 次域名不在白名单，1 次只拿到重定向）。
> 标注：「厂商自报」＝Anthropic 自己发布的数据；「自述」＝当事人自己报告、无第三方核实；「（推断）」＝本备忘录的推断；P1＝本地仓库核对。证据等级见第 6 节。

## 1. 一句话结论

高手和新手差的不是提示词，而是三件看得见的事——把 Claude 看不到的信息交给它、给它一个能跑出通过或失败的检查、把不能有例外的规则交给 hooks 和权限规则强制执行；收益大头在新手→中级（严格口径成功率 15%→28–33%），并行和定时只是放大器，委托人已到 L2、L3 做了一半，下一步该把现成的回查脚本变成强制闸门，而不是多开 agent。

## 2. 关键发现

1. **最大的一跳在新手→中级。** Anthropic 分析了约 40 万个交互会话（约 23.5 万人，2025-10 至 2026-04）。严格口径的"已验证成功"，新手 15%，中级及以上 28–33%；遇到麻烦时新手放弃率 19%，其他人 5–7%；从中级到专家，曲线基本走平。[S2，厂商自报]
2. **高手的每条指令带出更多工作量。** 新手每条提示约触发 5 个动作、产出约 600 词；专家约 12 个动作、约 3,200 词。研究判断专长看三个信号：指令是否精确、要求 Claude 验证什么、谁纠正谁；结论是"对领域有可用的理解，就拿到大部分收益"。[S2]
3. **验证是第一杠杆。** 官方 2026 版最佳实践的三条主线之一是"给 Claude 一个能跑的检查"，并要它拿出证据（命令、输出或截图），不要只听一句"测试都过了"。Claude Code 作者 Boris Cherny 自述：有了验证回路，最终质量能提升 2–3 倍。[S1；S4，自述]
4. **规则放错地方就会失效。** CLAUDE.md 和 skill 里的话，遵不遵守由 Claude 决定；hooks、deny 规则和 CI 由 harness 强制执行。官方标准：一行规则加粗后还被忽略，就该改成 hook。CLAUDE.md 建议 200 行以内。[S1]
5. **高手把人工把关前移到调研和计划。** HumanLayer 的 Dex Horthy 说，计划里错一行会变成几百行坏代码，调研里错一行会变成几千行；他把上下文用量控制在 40%–60%。他自述用 3 小时调研计划、4 小时实现写出约 3.5 万行代码（其中一个 PR 已合并），也公开了一个花 7 小时没做成的案例。[S9，自述]
6. **独立证据指向同一方向。** UCSD 对 13 场现场观察和 99 名资深开发者的研究发现：专业开发者不 vibe，而是先规划、再监督，并验证 agent 的全部产出 [S12]。METR 实验里资深开发者用 AI 反而慢 19%，事后却自认快 20% [S13]——自我感觉不能当进步的尺子。
7. **并行是放大器，不是起点。** agent teams 仍是实验功能，token 随队员数线性增长；顺序任务、改同一文件、依赖多的工作，用单会话或 subagent 更有效；建议 3–5 名队员、每人 5–6 个任务起步。subagent 只带来并行和"新眼睛"，不会让答案更聪明。[S19；S1]
8. **复利来自"每犯一次错就改环境"。** Boris 的团队共用一份 CLAUDE.md，每周更新好几次 [S4]；Mitchell Hashimoto 把这叫作 engineer the harness [S6]；Every 的"复利工程"要求每一单位工作都让后面的工作更容易，旗下 5 个产品基本都由单人工程团队维护 [S17]。
9. **非程序员同样吃得到红利。** Anthropic 增长营销团队用 2 个专职 subagent 处理广告 CSV，几分钟生成数百条变体，Figma 插件单批最多 100 个；法务、数据科学家也自建了工具。[S5，厂商自报]

### 3.2 新手和高手的可观测差别

| 观察点 | 新手 | 中级及以上 / 专家 | 来源 |
|---|---|---|---|
| 每条提示触发的动作 | 约 5 个 | 约 12 个（专家） | S2 |
| 每条提示的产出 | 约 600 词 | 约 3,200 词（专家） | S2 |
| 严格口径"已验证成功" | 15% | 28–33% | S2 |
| 至少部分成功 | 77% | 91–92% | S2 |
| 遇到麻烦后仍"已验证成功" | 4% | 15%（专家） | S2 |
| 遇到麻烦时放弃 | 19% | 5–7% | S2 |
| 怎么下指令 | 泛泛而谈，不带领域知识 | 带着对代码库和环境的具体了解 | S2 |
| 怎么验证 | 不提，或者只问一句"好了吗" | 说清楚验证什么，要命令输出或截图 | S2、S1 |

- **怎么读这组数字。** 这是厂商自报：专长和成败都由模型读会话记录判定，只含交互会话，不含 `claude -p`。"要求 Claude 验证什么"本身就是判定专长的信号之一，"已验证成功"又要求有硬证据，两者有一定重叠（推断）。稳妥的读法是：会提出验证要求的人，严格口径成功率约为新手的两倍（推断）。
- **独立证据一。** UCSD 的研究（13 场现场观察加 99 份问卷，受访者都有 3 年以上经验）发现，资深开发者先规划、再动手，验证 agent 的全部产出；他们认为 agent 适合描述清楚的任务，大约一半时间会改 agent 写的代码。局限是没有新手对照组。[S12]
- **独立证据二。** METR 2025 年的随机对照实验：16 名资深开源开发者、246 个任务，用 AI 耗时多 19%，事后却自评快 20%；2026-02 更新的估计接近持平，METR 自认数据不可靠。[S13] Simon Willison 的说法与此一致："AI 工具放大的是你已有的专长。"[S8]
- **一句话归纳**：高手先定义什么叫"完成"，再放手让它做；新手先放手，事后再猜它算不算完成。

### 3.3 进阶阶梯 L0–L5

这套分级综合了 S1、S2、S6、S7，验收标准是本备忘录提出的建议（推断）。和 Yegge 的阶段大致对应：他的 1–4 阶段约等于 L0–L1，5–6 阶段约等于 L2–L4，7–8 阶段对应 L5 里的编排部分；S2 说的"新手→中级"大致落在 L1→L3（推断）。

| 级别 | 典型行为 | 关键配置或能力 | 常见卡点 | 升级验收标准 |
|---|---|---|---|---|
| **L0** 聊天加复制粘贴 | 在网页聊天里要代码或文案，再手动贴进文件 | 无 | 每次都要重新交代背景；结果没法复现 | 连续 5 个小任务，都由 Claude 直接在项目里读写文件、跑命令完成 |
| **L1** 单会话 vibe coding | 一个会话从头聊到尾，看着差不多就收工 | 默认设置、auto mode | 一个会话塞好几件事；同一处纠正三四次；遇到阻碍就放弃 | 开工前写下"完成标准"；纠正两次还不对就 `/clear`，重写提示；收工时拿得出证据 |
| **L2** 上下文工程 | 先让 Claude 采访自己，写出 SPEC.md；在 plan mode 里定好计划再执行；一个任务一个会话 | 短 CLAUDE.md（200 行以内）、`.claude/rules/` 按路径生效的规则、用 skill 装流程知识、规格和计划文件 | CLAUDE.md 越写越长，靠加粗强调；流程闸门只写成文字，偶尔被跳过 | 新会话光读文件就能开工，不用口头补背景；CLAUDE.md 每一行都过得了"读代码看不出来"这一关 |
| **L3** 验证闭环加可复用资产 | 每个任务都有能跑出通过或失败的检查；没有例外的规则交给 hook；常用流程沉淀成 skill 和命令；diff 由没参与编写的 reviewer 来审 | Stop hook（退出码 2 打回）、PostToolUse 格式化、deny 规则、只读 reviewer subagent、`/code-review`、回归样例集 | 检查有了，但要靠 Claude 自觉去跑；把个人偏好也写成 hook；reviewer 的意见全盘照收，结果过度设计 | 交付物 100% 过机器检查，而且由 hook 来保证；同类错误不再出现第二次；新项目不用复制任何东西就能复用资产 |
| **L4** 并行与异步 | 几个独立任务各开一个 worktree 或云端会话，同时推进；subagent 负责检索和审查；用 `claude -p` 跑批量；用 `/loop` 盯 CI | `claude -w`、`.worktreeinclude`、限定工具的自定义 subagent（简单的活交给 Haiku）、`claude -p` 加 `--allowedTools`、`--permission-mode dontAsk`、`--max-turns`、GitHub Actions | 把紧耦合的任务硬拆开；人成了审阅瓶颈；token 成倍增长 | 同时推进至少 3 个独立任务，合并冲突可控；每个无人值守任务都答得上官方的"5 问"（完成标准、能否自检、能碰什么、什么让它停、谁来签收）；批量任务先拿 3 个样本试跑，再放量 |
| **L5** 系统化 | 定时 agent 每天自动产出；用 agent teams 做调研和评审；用评测集量化质量；用插件分发 skills 和 hooks；做复利工程 | `/schedule` 云端定时任务、TaskCompleted 等质量闸门、agent teams（实验功能）、评测基线、插件、`--max-budget-usd` 和 `/usage` | 成本失控；产出没人签收；编排器本身成了维护负担 | 定时任务连续 2 周无人干预，产出仍然合格；质量有基线数字，每周追踪；新人或新项目一天内装好整套流程 |

### 3.4 配置样例（不计入字数）

字段名按 S1、S19、S20 官方文档核对过。凡是标了"（推断，需自测）"的，都是根据委托人仓库改写的写法，用之前先在副本上试。

**① CLAUDE.md 骨架**（按 S1 列的四类内容写，每类只写 Claude 读代码看不出来的东西）

```markdown
# Commands（怎么验证）
- 页面地图：python3 .claude/skills/<skill>/scripts/page_map.py 报告.pdf
- 成品回查：python3 .claude/skills/<skill>/scripts/verify_pdf.py 成品.pdf --pages N
# Conventions（仓库里看不出来的决定）
- 字体、二维码、母本只从 skill 目录引用，不复制进项目目录
# Gotchas（容易误导的地方）
- 无头浏览器在沙箱里会静默失败（退出码 0 但不出文件），先看环境说明
# Corrected twice（已经纠正过两次的事）
- 大标题不得直译英文原标题
```

**② Hook：收工前强制回查**（`.claude/settings.json`；结构照搬 S1 的 Stop hook：退出码 2 表示不许结束，stderr 的内容会回给 Claude；连续打回 8 次后会被放行）

```json
{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command",
          "command": "python3 tools/check_new_pdfs.py 1>&2 || exit 2" } ] }
    ]
  }
}
```

`tools/check_new_pdfs.py` 要自己写：找出本次会话新生成的 PDF，逐份调用 `verify_pdf.py 成品.pdf --pages N --gap-fail`（页数不符、≥14mm 漏风都按 FAIL；残留词照他原设计只 WARN，但把清单打印出来），有任何一份 FAIL 就返回非 0（推断，需自测）。

**②b 可选：大纲没确认，就不许写成品 HTML**（PreToolUse 遇到退出码 2 会拦下这次工具调用，S20；脚本为推断，需自测）

```json
{ "hooks": { "PreToolUse": [ { "matcher": "Write",
    "hooks": [ { "type": "command", "command": "bash \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/outline_gate.sh" } ] } ] } }
```

```bash
#!/bin/bash
# .claude/hooks/outline_gate.sh
f=$(jq -r '.tool_input.file_path // empty')
case "$f" in
  */research_visual_digest/*.html)
    [ -f "$(dirname "$f")/OUTLINE_OK" ] || { echo "大纲未确认：先发一屏大纲，等用户回「行」" >&2; exit 2; } ;;
esac
exit 0
```

`OUTLINE_OK` 由本人在确认大纲后手动创建，不要让 Claude 代建；可以再加一条 deny 规则，禁止 Claude 写这个文件（写法以 permissions 文档为准）。Claude 仍可能绕道用 Bash 写文件，所以这道闸门是防遗忘，不是安全边界（推断）。

**③ Skill 骨架**（`.claude/skills/weekly-recap/SKILL.md`；`disable-model-invocation: true` 表示只能由本人输入 `/weekly-recap` 来启动，S1）

```markdown
---
name: weekly-recap
description: 汇总本周已交付的研报精华，生成目录和核对表。用户说"周报""本周汇总"时使用。
disable-model-invocation: true
---
1. 列出 research_visual_digest/ 下本周新增的目录；一个都没有就停下来说明。
2. 对每份成品跑 scripts/verify_pdf.py，FAIL 的单独列出，不进汇总。
3. 把标题、来源机构、页数写进 weekly/<日期>.md。
4. 只产出草稿，不发布。
```

**④ 只读 reviewer subagent**（`.claude/agents/digest-reviewer.md`；`tools` 只给只读工具，由 harness 强制执行，S1）

```markdown
---
name: digest-reviewer
description: 成品 HTML 写完、渲染 PDF 之前，对照原报告做独立审查。
tools: Read, Grep, Glob
---
你在审一份不是你写的研报精华。只回答四件事，每件都要给出页码证据：
1. 大标题是不是英文原标题的直译；2. 章节顺序是不是照搬原文；
3. 有没有至少一句原文没有的主线判断；4. 每个数字是否都有 src 注释。
不评价文风和排版。
```

**⑤ headless 接 cron**（参数照 S1：`--bare` 不加载 CLAUDE.md、skills 和 hooks，鉴权走 `ANTHROPIC_API_KEY`；跑到 `--max-turns` 上限会报错退出）

```bash
#!/bin/bash
# scripts/daily_intake.sh；crontab 里写：40 7 * * 1-5 /仓库路径/scripts/daily_intake.sh
cd "$(dirname "$0")/.." || exit 1
claude --bare -p "对 inbox/ 里新增的研报 PDF 逐份运行 .claude/skills/<skill>/scripts/page_map.py，把一屏大纲草稿写进 drafts/。只写草稿，不发布。全部完成回 OK，否则回 FAIL 加原因。" \
  --allowedTools "Read,Write,Bash(python3 *)" \
  --permission-mode dontAsk --max-turns 30 \
  --output-format json >> logs/daily.jsonl
```

不想用 API key 的话：在会话里用 `/schedule` 建一个云端定时任务（需要 claude.ai 登录；官方建议先给 main 加上任务绕不过去的分支保护，S1）。

**⑥ worktree 并行**（S1）


## 4. 反例、失败与局限

### 4.1 反模式（11 条）

| # | 反模式 | 出处或案例 | 解法 |
|---|---|---|---|
| 1 | 一个会话什么都塞 | 每次请求都重发整段对话：三个无关任务攒在一个会话里，做第四个时每轮都在为前三个付费 [S1] | 任务之间 `/clear`；要回头接着做，就先 `/rename` 存档 |
| 2 | 纠正个没完，或原样重跑碰运气 | 同一处纠正两次还不对，第三次只会让对话里多一条失败记录，应 `/clear` 后写一条吸收教训的新提示 [S1]；问题往往出在上游的调研和计划 [S9] | 回到计划层修正，再开新会话 |
| 3 | CLAUDE.md 过长、靠加粗 | 官方建议 200 行以内，堆 IMPORTANT 反而会让 Claude 把规则用过头 [S1]；HumanLayer 自家的根文件不到 60 行 [S16] | 只写读代码看不出来的东西；没有例外的规则改成 hook |
| 4 | 没验证就收工 | Claude 说做完了其实没做完，多半因为它没法自检 [S1]；Anthropic 的长任务实验里，agent 看到有进展就宣布完工 [S10]；新手的严格成功率只有 15% [S2] | 给它能跑的检查，并要证据；用 Stop hook 兜底 |
| 5 | 不看 diff，只看总结 | Claude 写的总结属于"由模型决定"的那一类，一句"All tests pass"说明不了什么 [S1]；METR 实验里，自我感觉和实测相差约 39 个百分点（由 -19% 与 +20% 推算）[S13] | 要命令输出或截图；让没参与编写的 reviewer 去看 diff |
| 6 | MCP 和工具堆太多 | 已经连上的 MCP 即使不用也占上下文 [S1]；Anthropic 的一个示例任务改用代码执行之后，token 从 15 万降到 2 千 [S15] | 在 `/mcp` 里关掉不用的；有命令行工具的优先用命令行 |
| 7 | 紧耦合的任务硬上多 agent | 官方：顺序任务、改同一文件、依赖多的工作，用单会话或 subagent 更有效；两个队员改同一文件会互相覆盖 [S19]；subagent 不会更聪明，有时反而更慢 [S1] | 先拿调研、评审这类边界清楚的任务做并行；按文件划分谁负责什么 |
| 8 | 用文字指令保护生产环境 | Replit 事件：用户明确下了"冻结"指令，agent 仍然删掉了生产库，而开发和生产共用同一个库 [S14] | deny 规则在任何权限模式下都生效 [S1]；再加沙箱、环境隔离，合并由人来批 |
| 9 | 成本失控 | 有用户让它 24 小时在后台跑，Anthropic 因此在 2025-07 加了周限额 [S18]；一个 3 人团队每月光 Opus 就花约 1.2 万美元 [S9]；agent teams 的 token 随队员人数线性增长 [S19] | 用 `--max-turns`、`--max-budget-usd` 封顶，用 `/usage` 看账；简单的活交给 Haiku |
| 10 | 把 harness 设计过度 | 官方：规则多到 40 条，大半是本可让 Claude 自己权衡的偏好；reviewer"总能挑出点什么"，照单全改会多出无用的抽象层 [S1] | 只给没有例外的规则上 hook；评审提示里写明"跳过风格问题" |
| 11 | 跳级上编排 | Gas Town 的作者本人说它只适合第 7–8 阶段的用户 [S7]；收益主要集中在新手→中级这一步 [S2] | 先过 L3 验收，再谈 L4、L5 |

### 4.2 证据的局限

- 卡片里的效果数字，要么是当事人自述（S4、S9、S11、S17），要么是厂商自报（S2、S5、S10），没有一条来自独立的对照实验。
- S2 用模型读会话记录来打分，看不到代码最后是否真被用上，也不含无头用法。
- 找得到的独立研究（S12、S13）研究的都是职业程序员；"内容创作者用 Claude 做出版物"这类场景，没有找到专门的研究。
- 高手的流程也会失败：Dex 公开了 7 小时没做成的案例 [S9]，Anthropic 承认 agent 看不到浏览器原生弹窗 [S10]。差别在于失败能被检查发现。

## 5. 对委托人的启示

1. **定级：L2 已完成，L3 做了一半（推断）。** 他的研报 skill 有四道闸门：开工先报运行目录、读护栏、跑页面地图、发一屏大纲等确认。另外还有检查页数、留白和残留词的回查脚本，以及覆盖报数脚本（P1）。按 S2 的三个信号（指令精确、要求验证、自己纠正 Claude），他已是中级以上，"停在小白"的自评不准。但"感觉没有很大提升"是真的：从中级到专家这段曲线本来就平（S2），剩下的提升不在提示词，在 harness 和异步运行。
2. **卡在"闸门只写成了文字"。** skill 文件自己记了 2 次"没读护栏，退化成了翻译"；2026-08-12 加上留白审计后回头重查，此前"已交付"的作品里有 8/10 页、10/13 页留白过大的（P1）。这正是 S1 说的情况：没有例外的规则放在提示里，只能保证大多数时候被遵守。另外，资产按项目复制（二维码、字体各 22 份），指令文件也有过多份拷贝，教训沉淀不到同一处，谈不上复利。
3. **下一步做三件事，按顺序来，每件 0.5–1 天：**
   - **① 把闸门改成 hook。** Stop hook：本次会话新生成的 PDF 过不了 verify_pdf.py（页数和 ≥14mm 漏风按 FAIL 级，残留词仍只提示），就不许收工。PreToolUse hook：大纲没确认，就不许写成品 HTML。样例见 3.4。验收：连续 10 份成品，没有一份退化成翻译，没有一份留白过大。
   - **② 把资产收到一处，建回归集。** 字体、二维码、母本只在 skill 目录留一份，构建脚本按路径引用。从已交付的成品里挑 5–10 份当"标准样本"，以后每次改 skill 或脚本，一键重跑 verify 和覆盖报数。他已经给覆盖报数脚本定了"跑满 5 份再定阈值"的规矩，这就是评测集的雏形。验收：新项目不再复制任何东西；改完之后几分钟内就能知道有没有退步。
   - **③ 加一个只读 reviewer 和一个定时任务。** reviewer subagent 先替他把自己定下的三道是非题过一遍、附页码证据，再查数字出处，最后仍由他拍板（样例见 3.4）。再用 `/schedule` 在工作日早上，对新入库的研报跑页面地图、出大纲草稿，等他确认，不自动发布，守住"不让 AI 托管发布"的红线；云端环境可以直接用仓库里已有的初始化脚本。验收：每周至少有 3 个早上能拿到可用的草稿。
4. **暂时别做的事。** 先不急着上 agent teams 或 Gas Town 那样的编排。他的产出是一份份可以各自独立完成的 PDF，很适合用 worktree 并行（L4）；但在 L3 的强制闸门建好之前，并行只会把没验证过的产出成倍放大（推断）。
5. **用数字看进步，不凭感觉。** 每份成品记三个数：第一次就通过 verify 的比例、被人工打回的轮数、从拿到 PDF 到交付用了多久。METR 的教训是，自我感觉和实测可能差出近 40 个百分点（S13）。
