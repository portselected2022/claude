# A1 · 用途地图：大家用 agent / 多 agent 做自动化，主要在解决什么问题

> 编制：A1（R1 并行取证）｜日期：2026-11-18｜检索：WebSearch 14 次、WebFetch 10 次（其中 2 次因 research.google、arxiv.org 被本环境网络策略拦截而失败）
> 说明：S1–S7、S10、S11、S17、S18 是 Anthropic 自有数据或产品说明，一律视为**厂商自报**。总表中的架构建议和成熟度判断是 A1 的综合判断（推断）。

## 1. 一句话结论

agent 的主战场仍是写代码（公开 API 上 agent 工具调用约一半是软件工程）。2025→2026 年，用途在向操作软件、写作、数据分析和后台流程外溢，"整件交给 AI"越来越多地发生在 Claude Code、Cowork 这类 agent 产品里。多 agent 只在"可并行、广度优先、值得多花十几倍 token、且有可靠校验"的任务上明显占优；遇到顺序任务、多方共改一个产物时反而掉分。所以小团队的默认做法应是"单 agent + 固定工作流 + 自动校验"，多 agent 只用在前置的广度研究上。

## 2. 关键发现

1. **编码仍是第一用途，但份额在被稀释，并迁往 agent 产品。** Claude.ai 上"计算机与数学"类从 2025-03 峰值 40% 降到 2025-11 的 34%，教育类从 9%（2025-01）升到 15%；同期 API 上该类从 44% 升到 46% [S2]。2026-02 数据显示，编码继续从 Claude.ai 迁往 1P API（含 Claude Code），Claude.ai 前十任务的占比从 24% 降到 19% [S3]。
2. **在 Claude Code 内部，用途从"修 bug"转向"操作软件 + 写作 + 数据分析"。** 2025-10 至 2026-04 约 40 万个交互式会话（约 23.5 万人）中，修 bug 的占比从 33% 降到 19%，操作软件从 14% 升到 21%，写作与数据分析合计从约 10% 升到约 20% [S5]。
3. **聊天端的自动化与增强来回摆动，委托在向 agent 产品集中。** Claude.ai 指令式对话从 27%（2025-01）升到 39%（2025-08），又回落到 32%（2025-11）；2025-11 增强重回 52%，自动化为 45%。1P API 约四分之三是自动化，指令式占 64% [S2]（2025-09 报告称企业 API 77% 为自动化 [S4]）。2026 年 4–6 月的数据显示，同类产出在 Claude Code 上的自主度在 31 类中有 26 类更高，平均高 0.37 分（5 分制）。写博客文章，在 chat/Cowork 中位要来回 13 轮，在 Claude Code 里只需 1 次人工提示；约三分之二的差距来自同样的任务在 agent 产品里交出去更多 [S1]。Claude Code 第 99.9 百分位的单轮运行时长从不到 25 分钟升到 45 分钟以上（2025-10→2026-01）[S6]。（主协调提供的"Claude Code 79%、Claude.ai 49% 含自动化"本轮未复核，方向一致。）
4. **agent 的真实落地高度集中在软件工程和后台流程。** 在 99.8 万次公开 API 工具调用的抽样里，软件工程近 50%，商业智能、客服、销售、金融、电商各自不超过几个百分点 [S6]。API 的非编码用途集中在邮件分类、发票处理、B2B 冷邮件这类后台流程 [S2]。行业调查方向一致：部门级 AI 支出的 55%（约 40 亿美元）花在编码上 [S15]；LangChain 受访者把客服（26.5%）和研究与数据分析列为首要 agent 用例 [S13]；McKinsey 称 agent 最常见于 IT 与知识管理 [S14]。
5. **规模化仍是少数，人仍在环。** McKinsey 的调查里，23% 的企业已在某处规模化 agent，39% 在试验，但任何单一职能中规模化的比例都不超过 10% [S14]。Stack Overflow 的调查里，52% 的开发者不用 agent 或只用更简单的 AI 工具；agent 用户中 69% 认为提效，只有 38% 认为代码质量提高；46% 不信任 AI 输出的准确性 [S16]。Anthropic 自己的测量是：80% 的工具调用至少有一种保护措施，约 73% 可能有人在环，仅 0.8% 不可逆；Claude Code 新用户约 20% 的会话全自动批准，用到 750 个会话后升至 40% 以上 [S6]。
6. **任务越长越不可靠。** API 任务成功率从 1 小时以内的约 60% 降到 5 小时以上的约 45%，约 3.5 小时处跌破 50%；Claude.ai 有多轮反馈，外推要到约 19 小时才跌破 50%。按成功率修正后，估算的年化生产率增益从 1.8 降到约 1.0 个百分点 [S2]。
7. **多 agent 的收益来自"可并行 + 多花 token"，代价也在这里。** Anthropic 的研究系统（Opus 4 做主 agent，Sonnet 4 做子 agent）在内部评测上比单 agent 高 90.2%，但 token 约为聊天的 15 倍，BrowseComp 上 token 用量单独解释 80% 的表现差异；"大多数编码任务"因为要共享上下文、依赖多而不适合 [S7]。Google 等对 180 种配置做了对照：在可并行的金融推理上，集中式协调提升 80.9%；在严格顺序的规划任务上，所有多 agent 变体下降 39%–70%；各自独立并行的多 agent 把错误放大 17.2 倍，集中式为 4.4 倍 [S12]。
8. **并行写代码要靠"可切分 + 近乎完美的验证器"。** 16 个 Claude 用两周、近 2,000 个会话、不到 2 万美元，写出约 10 万行 Rust 的 C 编译器，能编出可启动的 Linux 6.9。但遇到"编内核"这种单一大任务时，所有 agent 撞上同一个 bug、互相覆盖修复，直到用 GCC 作对照把问题切小，才恢复并行 [S10]。官方 agent teams 文档把适用场景限定为研究评审、独立模块、竞争假设调试和跨层协调，并写明顺序任务、同文件编辑、依赖多的工作用单会话或 subagent 更好 [S11]。Cognition 主张默认单线程，并共享完整轨迹 [S8]。
9. **金融用途已被产品化，但公开的效果数据几乎都是厂商自报。** Anthropic 在 2025-07 至 2026-02 推出了三层产品：一是数据连接器（S&P Capital IQ、PitchBook、LSEG、Moody's、Aiera、FactSet、MSCI 等）；二是 Claude for Excel 和 6 个预置 Agent Skills（可比公司、DCF、尽调数据包、公司简介、业绩分析、首次覆盖报告）；三是 Cowork 角色插件（投行、股票研究、PE、财富管理）[S17][S18]。量化结果只有两条：Block 称 75% 的工程师每周省 8–10 小时以上（SQL agent），Sonnet 4.5 在 Finance Agent 基准上准确率 55.3% [S17]。Evident 指数覆盖的 50 家大行中，只有 9 家披露了处于试点或生产阶段的 AI agent [S19]。

| 方向 | 典型任务 | 证据强度 | 单 agent / 多 agent / 工作流 | 成熟度 |
|---|---|---|---|---|
| 软件开发 | 写功能、修 bug、重构、测试 | 强（E1：S2、S5、S6；E3：S15、S16） | 单 agent 为主；能切成独立模块时用多 agent | 已规模化 |
| 操作软件与环境 | 装依赖、配环境、跑脚本、运维 | 中（E1：S5） | 单 agent | 已规模化（开发者群体内） |
| 广度研究与信息综合 | 多来源检索、横向对比、综述、核查 | 强（E1：S7；E3：S13） | 多 agent（主 agent 分派，子 agent 并行） | 已规模化（产品功能）；企业内试点 |
| 写作与内容生产 | 报告、文章、营销文案 | 中（E1：S1、S5） | 单 agent + 模板与闸门工作流 | 已规模化（人审） |
| 数据分析与表格 | 清洗、统计、建表、看板 | 中（E1：S1、S5） | 单 agent，人在环（这是唯一一类聊天端自主度高于 Claude Code 的产出） | 试点→规模化 |

| 评审与排错 | 多视角代码评审、竞争假设调试 | 中（E1：S11；E3：S9） | 多 agent（agent teams 或多个评审 subagent） | 试点（实验功能） |

| 无人值守的"全自主团队/公司" | 全流程自动接单、发布、互动 | 弱（反证：S6、S14、S16） | — | 炒作为主 |

## 3. 可以直接照做的做法

**3.1 判断规则：任务特征 → 架构**

| 任务特征 | 选择 | 依据 |
|---|---|---|
| 步骤和格式固定、每天重复、出错代价高 | 固定工作流：用脚本或 skill 串起来，模型只做其中的判断步骤，结尾跑校验 | S2、S6（推断） |
| 广度优先、子问题互不依赖、材料超出一个上下文 | 多 agent：主 agent 分派，子 agent 并行，结果回收汇总 | S7、S12 |
| 强顺序依赖、要共享全部上下文、多方改同一个产物 | 单 agent；subagent 只做查询和核对，不写产物 | S7、S8、S11、S12 |
| 需要互相挑刺的评审、根因不明的排错 | agent teams 或多个评审 subagent，每个只看一个视角 | S11 |
| 能切成大量小任务，且有近乎完美的自动测试 | 多 agent 并行，用锁文件或任务表认领 | S10 |
| 价值低的日常小事 | 单会话 | S7、S11 |

**3.2 Claude Code 里的落地步骤**（适用：已有 skill、有重复任务的个人或小团队）

1. 先用 subagent，不急着上 agent teams。subagent 的结果回到主会话，更省 token；文档建议新手先从"不写代码的研究和评审"做起 [S11]。
2. 确实需要 agent teams 时：在 settings.json 的 env 里设 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`；起步 3–5 个队友，每人 5–6 个任务，每个队友负责不同的文件；在派生提示里写清背景，因为队友不继承主会话的历史；用 `TaskCompleted`、`TeammateIdle` 两个 hook 做质量闸门，退出码 2 即打回 [S11]。
3. 给每个子 agent 写清四件事：目标、输出格式、可用工具、边界。人数按复杂度配：简单事实查询 1 个 agent、3–10 次工具调用；对比类 2–4 个子 agent；复杂研究 10 个以上 [S7]。
4. 评测从约 20 条真实样本起步，用 LLM 评审按 0–1 打分并判通过与否，再加人工抽查。人工抽查曾发现 agent 偏爱 SEO 内容农场 [S7]。
5. 把长任务切成 1 小时以内的段落，每段都有可检查的产出（依据 S2 的成功率曲线，推断）。
6. 控制上下文污染：程序只打印几行摘要，细节写进日志，"ERROR"和原因写在同一行，方便 grep；给测试加 `--fast` 抽样模式，只跑 1% 或 10% [S10]。

## 4. 反例、失败与局限

1. **顺序任务上，多 agent 掉分。** 在严格顺序的规划任务上，所有多 agent 变体都下降 39%–70%；各自独立并行时，错误放大 17.2 倍 [S12]（E3，原文域名在本环境被拦截，未读原文）。
2. **派单失控。** Anthropic 早期版本会为简单问题派出 50 个子 agent；委托写得含糊时，子 agent 之间重复劳动 [S7]。
3. **并行在单一大问题上失效。** C 编译器项目里，16 个 agent 同修一个内核 bug，互相覆盖。成品没有自己的汇编器和链接器，16 位 x86 部分还要调用 GCC；生成的代码即使全开优化，也不如 GCC 关闭优化。作者提醒，"通过测试"不等于完成 [S10]。
4. **上下文被切碎，子任务会被误解。** Cognition 用 Flappy Bird 的例子说明：子 agent 只拿到自己那一块，就会误解子任务，合并时难以调和 [S8]（E3）。
5. **agent teams 仍是实验功能。** `/resume` 不恢复队友；任务状态会滞后，卡住依赖它的任务；lead 可能提前宣布完成；非交互模式（`-p`、Agent SDK）下不会生成队友 [S11]。
6. **数据本身有偏差。** Anthropic 的问卷（约 9,700 人）明确不具代表性，偏向知识工作者 [S1]；2026-01 报告不同章节的类别口径不一致 [S2]；LangChain 受访者主要来自它自己的生态 [S13]；金融产品页只有客户证言，几乎没有可复核的数字 [S17][S18]。

## 5. 对委托人的启示

1. **主流程不要拆成多 agent。** "一份研报 → 一份中文可视化 PDF"是单一产物、强顺序、要求风格一致的任务，正落在 S7、S8、S11 都认为不适合多 agent 的区间。v3 skill 的闸门流程应继续由单 agent 跑。并行只放在前置的"读材料"环节：同一公司的 3–5 份投行研报，各派一个 subagent，按固定格式（数字、页码、原句）抽取，再由主 agent 汇总比对（推断）。
2. **先把验证器接成自动闸门，再谈并行和无人值守。** 他已有的 PDF 机器回查和覆盖报数脚本，就是 S10 所说"近乎完美的验证器"的雏形。下一步是用 hook 在每次产出后自动运行这两个脚本，不通过就打回。没有这一步，多 agent 只会更快地产出错误（推断）。
3. **每日数据环节做成固定工作流，不做开放式 agent。** 行情和一致预期接口已经接好，可以写成"每日 1 张数据卡"（如评级变动、一致预期修正）的脚本，人审后手动发布。这属于 API 侧已经规模化的后台流程形态 [S2]，也不碰"不用 AI 自动发布"的红线（推断）。
4. **skill 扩展可以直接对照官方的金融任务清单。** 业绩会纪要解析、按新指引更新预期、可比估值、首次覆盖框架，都是 Anthropic 为股票研究员预置的任务 [S17][S18]。他可以只做"机构怎么说、数字怎么变"的可视化版本，不给买卖结论，守住不荐股的红线（推断）。
5. **从"有活时集中对话"转向"一次说清的委托"。** 同一篇博客，在聊天里中位要 13 轮，在 Claude Code 里只要 1 次提示 [S1]；写作和数据分析正是 Claude Code 里增长最快的非编码用途 [S5]。把常用指令沉淀成 skill 和命令，目标是每个任务 1–2 次提示完成，并把任务控制在 1 小时以内、可检查的粒度 [S2]（推断）。
